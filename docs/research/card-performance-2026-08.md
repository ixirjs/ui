# Why ixir Card trails shadcn-svelte on SSR

**Date:** 2026-08-16  
**Scope:** the compare harness's default, four-element Card on server rendering  
**Result:** `17.0 µs/card` for `@ixirjs/ui` vs `13.0 µs/card` for shadcn-svelte (**1.31×**)

## Executive summary

This is not a class-merging or output-size problem. The benchmark gives both libraries four public
component boundaries, but the components do different work:

- shadcn's Card parts are independent styled elements: destructure props, call `cn`, emit markup;
- ixir's Card is a coordinated compound: construct/share a Bond, activate a relationship capability,
  resolve context and semantic node identity, register the meaningful parts, resolve the Kernel
  presentation lane, then dispatch a render branch.

The fixture uses none of Card's interactive or consumer-customizable features, so ixir pays their
setup cost while shadcn has no equivalent work. Current evidence attributes the residual gap to the
combined fixed Bond cost and repeated Kernel/context/render-dispatch cost—not one dominant slow
function.

The old 10× Card gap documented in `../compare/DIAGNOSIS.md` is historical. Registry, presentation,
and renderer-path changes have reduced it to 1.31×. The remaining gap is small enough that only
interleaved A/B experiments should decide changes.

## Evidence

### 1. Current comparative result

From `../compare/results/micro.json`, generated by taking the slope between 100 and 800 instances
(25 samples at each endpoint):

| Component     |         ixir |       shadcn | ixir / shadcn | ixir bytes | shadcn bytes |
| ------------- | -----------: | -----------: | ------------: | ---------: | -----------: |
| plain control |      1.30 µs |      1.40 µs |         0.93× |        114 |          114 |
| Button        |     12.20 µs |     13.73 µs |         0.89× |        496 |          892 |
| Badge         |      6.43 µs |      8.19 µs |         0.79× |        221 |          643 |
| Card          | **17.00 µs** | **13.00 µs** |     **1.31×** |    **663** |      **980** |

Button and Badge disprove a general ixir or preset-class problem. Card emits 32% fewer bytes yet is
slower, so response size is not the cause either.

`../compare/results/parts.json` locates the overhead across the compound:

| Shape               |     ixir |   shadcn |       gap |
| ------------------- | -------: | -------: | --------: |
| root only           | 13.60 µs |  9.75 µs |  +3.85 µs |
| full four-part Card | 29.33 µs | 13.88 µs | +15.45 µs |

This task times one 800-instance endpoint and is noisier than the micro slope. Its useful finding is
structural: the tax exists at the root and grows as Kernel-authored descendants are added. The
heterogeneous `card1..card4` sequence is not evidence of algorithmic complexity.

### 2. Equivalent-output ceiling ablation

`bun run bench:ceiling` was run three times on clean `b7f36e10`. The benchmark's `fast` arm keeps the
same public component boundaries, IDs, preset lookup, class merge, elements, classes, and text, but
removes Bond, Atom/semantic registration, capabilities, and the general presentation path.

Median of the three runs:

| Arm                         | µs/card | bytes/card | anchors/card |
| --------------------------- | ------: | ---------: | -----------: |
| plain handwritten floor     |    0.13 |        130 |            0 |
| equivalent fast arm         |    5.81 |        574 |            9 |
| real Card                   |   14.65 |        652 |           19 |
| fast arm under global Root  |    6.12 |        576 |            9 |
| real Card under global Root |   15.48 |        654 |           19 |

The removable machinery costs about **8.8–9.4 µs/card (60%)** against this internal ceiling. That is
an upper bound, not a proposed optimization: the fast arm obtains its speed by deleting public Card
capabilities. The remaining ~5.7 µs over handwritten markup is the cost of component boundaries,
seed/IDs, preset lookup, and class merging.

The global `<Root>` adds only ~0.8 µs/card. It is not the present bottleneck.

### 3. Sustained CPU profile

Fresh 8-second saturated profiles of `/micro?kind=card&n=400` served:

- ixir: **966 requests**;
- shadcn: **1,669 requests**.

The profiles are whole-server samples; ETag hashing and other per-request work scale with the number
of requests, so percentages cannot be compared directly. Normalizing selected self-time by rendered
cards shows where ixir's additional work accumulates:

| Selected self-time                | ixir µs/card | shadcn µs/card | Interpretation                                            |
| --------------------------------- | -----------: | -------------: | --------------------------------------------------------- |
| Svelte context lookup             |         1.44 |    not visible | Bond/preset context reads per compound/part               |
| Kernel native branches            |         1.05 |              — | `divBranch` + `headingBranch` dispatch                    |
| Kernel attrs                      |         0.39 |              — | ID/debug/semantic/rest attribute packet                   |
| Kernel node/create/render helpers |        ~0.51 |              — | repeated general render seam                              |
| GC                                |         3.63 |           2.81 | ~0.82 µs/card extra allocation pressure                   |
| Svelte component close/traversal  |         2.02 |           1.31 | extra snippet/render structure despite equal public parts |

No single helper owns the 4 µs marginal gap. The cost is distributed through context reads,
short-lived objects/closures, generic branch dispatch, attribute assembly, and the extra Svelte
render structure.

## Source-level explanation

### shadcn's path

Each file under `../compare/apps/shadcn/src/lib/components/ui/card/` independently:

1. destructures element props;
2. computes `cn(baseClass, className)`;
3. emits one literal element and its children.

There is no shared Card model, context lookup, semantic relationship, registration, generated
cross-part ID, capability lifecycle, renderer escalation, or preset layer.

### ixir's root path

`src/lib/components/card/card-root.svelte` additionally:

1. creates an SSR-deterministic identity seed;
2. builds reactive-accessor state for `disabled` and `clickable`;
3. constructs `CardBond`;
4. installs/activates `labelledControl`;
5. publishes Bond context and owns teardown;
6. builds a `KernelNode` with semantic attrs and interaction handlers;
7. resolves preset/class/attrs and dispatches the selected Kernel branch.

This explains the root-only +3.85 µs seen in the parts result.

### ixir's descendant path

`Card.Header`, `Card.Title`, and `Card.Body` each create a `KernelNode`, read Card context, resolve a
class/preset lane, assemble attrs and dispatch a branch. Header and Body are already marked inert by
`defineBond`, so they skip Atom construction and registration. Title remains semantic because it is
the root control's label.

That distinction matters: `registerLazy` accounts for only about **0.10 µs/card** in the profile.
The old registry problem is fixed; removing registration again cannot close today's gap.

The real Card also emits 19 hydration anchors against 9 in the equivalent fast arm. Those anchors
are evidence of the extra render/snippet structure and add SSR serialization plus later hydration
work. They are not explained by output volume: even with them, ixir's complete Card response is
smaller than shadcn's.

## What is not responsible

1. **Tailwind/class merging.** ixir Button and Badge beat shadcn; `mergePreset` and `getPreset`
   together account for only ~0.30 µs/card in the sustained profile.
2. **HTML size.** ixir emits 663 B/card vs shadcn's 980 B/card.
3. **The global Root provider.** The clean ablation prices it at ~0.8 µs/card.
4. **Quadratic registration.** The registry was replaced; Card's inert slots do not register, and
   the remaining registration self-time is ~0.10 µs/card.
5. **One obvious hot loop.** CPU is spread across many small generic operations and allocation/GC.

## Recommended next experiments

Do not special-case Card into shadcn-style wrappers: that would win by deleting the Bond contract,
not by making it cheaper. Optimize the shared Kernel path, and accept a change only after a
byte-equivalent interleaved A/B.

Priority order:

1. **Remove render-dispatch structure, not semantics.** Test whether the common literal `div`/`h3`
   lane can avoid the extra Kernel snippet/anchor while retaining rich-renderer escalation. The
   exact gate is unchanged elements, classes, IDs, attrs, handlers, and lifecycle behavior.
2. **Reduce repeated context reads.** Prototype one combined render-environment read or pass the
   already-resolved Bond through the family subtree. Target ceiling: the measured 1.44 µs/card, not
   the whole gap. This is architecture-wide and must preserve nested provider behavior.
3. **Reduce temporary packets.** A/B the `source`, prepared attrs/rest, and root semantic attrs
   allocations. GC is ixir's largest clear excess (~0.82 µs/card), but prior class/prototype
   rewrites have regressed performance, so do not infer wins from allocation counts alone.
4. **Isolate root setup last.** Measure Bond construction, `labelledControl`, and context share as
   separate ablation arms before considering lazy setup. Snippet contents are opaque at root init,
   so a safe "only create a Bond when needed" condition is not currently evident.

Success should be judged against `bench:micro`, `bench:parts`, `bench:ceiling`, SSR fingerprints,
and anchor budgets. A 4 µs gap is below the confidence of one ordinary run; use at least three
interleaved runs.

## Measurement caveat

The compare app consumes `link:@ixirjs/ui`. Its generated report still records tarball provenance
for commit `51c047d3`, while this run rebuilt linked `dist` from the `b7f36e10` checkout with
pre-existing uncommitted work. The successful compare build and profiles represent that linked
build, but the report's tarball SHA is not its identity. Published numbers should begin with
`bun run setup` so provenance and subject cannot diverge.

The active working tree entered a separate render-operand refactor during this investigation and
currently fails `bench:ceiling` with `TypeError: view.class is not a function`; the three ceiling
runs above therefore used a detached clean worktree and did not modify or benchmark that partial
refactor.
